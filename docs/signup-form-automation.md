# Autonomous signup form automation: Parts 12-13

## Scope

Parts 12-13 stop at a filled and locally verified signup form. They do not click
the signup submit control, accept legal terms, solve CAPTCHA, perform phone
verification, or claim that an account exists.

The value-free resolver lives in `ops/signup_forms.py`; the Playwright adapter
lives in `ops/playwright_signup.py`. The flow is coordinated with the durable
signup state machine through `ops/autonomous_signup_foundation.py`.

## Research basis

The design follows the primary browser and accessibility guidance:

- Playwright recommends user-facing locators such as role, label, placeholder,
  and test ID rather than brittle DOM structure:
  https://playwright.dev/python/docs/locators
- Playwright locators are strict for single-element operations, and its
  documentation warns that `first`, `last`, and `nth` can silently target the
  wrong element as a page changes:
  https://playwright.dev/python/docs/locators#strictness
- Playwright's `fill` and `select_option` APIs provide actionability checks for
  native inputs and selects:
  https://playwright.dev/python/docs/input
- Playwright screenshot masking is useful defence-in-depth, but secret-bearing
  pages in this project disable capture instead of treating masking as an
  authorization boundary:
  https://playwright.dev/python/docs/screenshots
- WAI-ARIA guidance treats accessible names as the mechanism that distinguishes
  controls and recommends native labels for form fields:
  https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/

## Part 12: deterministic detection

Playwright extracts a bounded, value-free snapshot of visible controls. The
snapshot never reads an input's current value.

Each semantic field is resolved in this exact order:

1. reviewed test ID from the active automation contract
2. accessible label
3. accessible role and name
4. associated HTML label
5. placeholder
6. reviewed nearby heading from the active contract

The first strategy with any matches is authoritative. It must produce exactly
one compatible control. Zero matches continue to the next strategy; multiple
matches safe-stop. A control token may belong to only one semantic field. Any
visible required control that cannot be mapped also safe-stops, so contract
drift cannot be ignored.

The detector does not use:

- screen coordinates
- XPath
- `nth()`, `first`, or `last` to break ambiguity
- model-generated CSS selectors
- raw HTML or page text in an LLM prompt

After inspection, each unique control is tagged with a random
`data-ops-signup-ref` token generated by trusted code. Part 13 resolves that
exact token and again requires a single live element, preventing a stale or
rerendered control from being filled accidentally.

## Part 13: deterministic fill and verification

The fill phase consumes:

- the detected, value-free `SignupFormInspection`
- the same active contract version
- session-bound `ApprovedRunValues`
- the exact `SignupAccountBinding`
- `SignupCredentialManager`
- the browser-service-local encrypted secret store

All required values and reviewed select rules are planned before the first field
is changed. A missing required value returns `configuration_required` without
partially filling the form.

The generated password reference is accepted only when
`SignupCredentialManager` returns the same reference for the exact account
binding. Email and password plaintext are resolved only inside the trusted
browser process.

Before either secret enters the DOM, screenshot capture is disabled for the
session. Field verification compares inside the page execution context and
returns only a boolean. No password, email address, vault reference, input value,
or page HTML is included in the inspection, result, prompt-safe projection,
log, or durable state.

Native `select` controls require a reviewed contract rule specifying whether to
match an approved or fixed option by label or by value. Custom comboboxes
safe-stop for later reviewed handling.

On a fill or verification failure, any secret controls already changed are
cleared best-effort. On success, the result is
`signup_form_filled_and_verified`, `submit_clicked` remains false, and the
durable state advances only to `signup_submission_ready`.
