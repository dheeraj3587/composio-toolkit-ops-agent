# Dark DEV-mode operations workspace with progressive run controls

This frontend refactor replaces the light editorial surface with a compact, forced-dark Composio DEV workspace and reorganizes the dashboard, run form, run detail, login, and shared primitives around that system. The run APIs and server actions are unchanged: backend projections still authorize mutations, plan-only runs still suppress live execution, and one-time secrets still cross the existing server boundary. Browser selection now moves under Advanced settings, while run evidence, provider/security state, retry controls, and audit history move into closed native disclosures. Several presentation choices now obscure security-relevant context or render critical state incorrectly.

**Watch for:** **Blockers:** [confirmed] warning and error foregrounds fall to roughly 1.0–1.6:1 contrast under the remapped dark palette; [confirmed] account-creation approval is visible before the committed provider profile it authorizes; [confirmed] the self-hosted-versus-managed browser boundary is auto-selected inside a closed disclosure; [confirmed] “Active now” counts plan-only completions and only the returned 25-run page. **Non-blocking:** [confirmed] research/validation retries and timeline-fetch failure have no cue outside closed disclosures; [confirmed] new optional markers are hidden from assistive technology while required fields remain unmarked; [confirmed] the passing tests do not exercise the new authority-sensitive disclosure states or computed contrast.

## High-level view

The document and shared primitives move to one dark system, but the palette assigns dark colors to low-numbered semantic shades and then uses those shades as text. **Blocker, confirmed:** backend-unavailable warnings, missing-field alerts, signup readiness, and destructive alerts become effectively unreadable, including sign-in errors.

The run form consolidates target, account, and company context while retaining automatic expansion for hidden-field errors. **Blocker, confirmed:** the browser provider now lives in the initially closed Advanced disclosure even though it distinguishes self-hosted Playwright from managed-cloud Browser Use and is automatically selected before submission.

The run detail page keeps backend-projected primary actions and onboarding controls prominent while moving reference material into disclosures. **Blocker, confirmed:** the admission decision remains prominent but its committed provider profile—domain, allow-list, billing/approval requirements, and evidence—has moved into a later closed disclosure, so account creation can be approved without the context the profile digest is intended to bind.

The dashboard adds direct System navigation, expands attention states to include blocked and failed runs, and moves the catalog below recent activity. **Blocker, confirmed:** its new “Active now” metric is a frontend inference over the default 25-item list response and ignores `execution_mode`, so a completed plan-only run at `route_selected` is reported as active. The shell’s anchor-aware state avoids double-highlighting Overview and Apps; removing Authenticator does not strand a route because no such frontend route exists.

Authentication behavior does not change. The revised tests remove a stale TOTP claim that the production action never enforced and assert the existing HTTP-only, Secure, SameSite=Strict session cookie; this remains a username/password boundary.

<summary>Details</summary>

### Dark semantic foregrounds are unreadable (**blocker, confirmed**)

`globals.css` redefines `amber-100` as `#30240e`, `emerald-100` as `#102d20`, and `red-200` as `#6f2c32`; those are dark fill colors, not dark-surface foregrounds. Dashboard and run-detail warnings use `text-amber-100` and `/70`, account-creation readiness uses `text-emerald-100` and `/65`, and destructive alerts use `text-red-200` and `/75`. Against the translucent dark fills, contrast is approximately 1.0–1.6:1, far below 4.5:1. Authentication failures and lockout messages, backend outages, missing configuration, run-creation errors, and “Connected signup inbox ready” are affected (`web/src/app/globals.css`, `web/src/components/ui/alert.tsx`, `web/src/app/page.tsx`, `web/src/app/runs/[runId]/page.tsx`, `web/src/components/new-run-form.tsx`).

The same pass introduces 9px `text-muted-foreground/65` shell and login chrome at about 3.8:1 against the rail. Semantic foreground tokens should remain light in dark mode, with separate fill tokens or explicit high-numbered text shades; a browser-level contrast audit should cover the composited states.

### Browser runtime choice is hidden despite changing the trust boundary (**blocker, confirmed**)

`NewRunForm` places `BrowserEngineField` inside the closed Advanced disclosure. It chooses Playwright whenever selectable and otherwise falls back to Browser Use, while the option copy identifies these as “Self-hosted” and “Managed cloud.” Closing the disclosure does not disable the radios, so the default provider and any account email/password are submitted together even when the operator never sees where the browser session will run (`web/src/components/new-run-form.tsx`, `web/src/components/browser-engine-field.tsx`).

The provider determines which runtime receives transient sign-in material and hosts the browser session. Keep the selector progressive if desired, but surface the selected runtime and its self-hosted/managed boundary beside submission; a managed fallback should be explicit.

### Admission approval no longer presents the committed profile first (**blocker, confirmed**)

The old onboarding layout placed `ProviderProfilePanel` beside `OnboardingFocusPanel`, immediately above `OnboardingControlBar`. The new layout leaves `AdmissionDecisionForm` in the always-visible control bar but moves `ProviderProfilePanel` into the later, initially closed “Providers and security” disclosure. “Create an account” is therefore offered with a profile digest while the registrable domain, allowed hosts, signup route, approval and billing requirements, credential flows, confidence, and evidence are hidden by default (`web/src/app/runs/[runId]/page.tsx`).

The digest is intended to bind the answer to the profile the operator was shown. If profile retrieval fails, the approval can still render from backend capabilities while only a collapsed unavailable panel records the missing context. Keep the profile adjacent to admission, auto-open it when `can_decide_admission` is true, or withhold approval until the profile is visibly available.

### “Active now” is not the backend-authoritative population it claims (**blocker, confirmed**)

The new dashboard metric treats every status except completed, failed, blocked, and configuration-required as active. `RunProgress` intentionally treats a plan-only run at `route_selected` as complete, but the dashboard counts that record as active because it never checks `execution_mode`. The count also comes from `listRuns()`’s default `limit=25` item page while the neighboring Integrations metric uses the backend’s full `total`, so the cards describe different populations without saying so (`web/src/app/page.tsx`, `web/src/lib/api.ts`, `web/src/lib/types.ts`).

Exclude `plan_only` records and label the metric as applying to the returned page, or source a true workspace count from a backend aggregate.

### Retry authority and audit failure are discoverable only after expansion (**non-blocking, confirmed**)

Research and credential-validation retries move from the visible output area into a closed “Output and retry authority” disclosure, even when one is enabled, while the visible progress card only says the run needs attention. Browser and email retries remain visible, creating an asymmetry based on the failed phase. Timeline retrieval failure is likewise represented only inside the closed audit disclosure (`web/src/app/runs/[runId]/page.tsx`).

Add an enabled-action or unavailable-audit cue to the summary, or open the relevant disclosure when it contains the only recovery action or an error.

### Form requirement semantics are visual-only (**non-blocking, confirmed**)

The new `Field` helper adds “(optional)” labels but marks them `aria-hidden`, while schema-required controls under `noValidate` have neither native `required` nor `aria-required`. Sighted users get the distinction; assistive-technology users do not. The callback field in the owner credential form receives the same hidden optional treatment, although its sibling inputs retain native `required` (`web/src/components/new-run-form.tsx`, `web/src/components/browser-hitl-forms.tsx`).

Expose the optional text to assistive technology and mark schema-required controls programmatically.

### Tests validate DOM presence, not the new disclosure decisions (**non-blocking, confirmed**)

The user reports test, lint, typecheck, and production-build passes, and `git diff --check -- web` is clean. Form assertions can find controls in closed `<details>` because they remain in the DOM; run-detail tests have no onboarding/admission case, and status tests assert Tailwind classes rather than rendered contrast. No dashboard case combines `plan_only` with `route_selected` or a response whose `total` exceeds its items.

Add interaction tests for provider disclosure, admission/profile ordering, retry discoverability, and plan-only counts. Contrast needs a real-browser accessibility pass because DOM-unit tests cannot validate composited colors.
