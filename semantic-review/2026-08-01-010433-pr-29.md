# Dark DEV-mode operations workspace with guarded run controls (v2)

This pass verifies the fixes for dark-mode legibility, browser-runtime disclosure, profile-bound admission, and the recent active-run metric. The committed profile now precedes admission and exact digest equality gates the decision form; recent active runs exclude plan-only records and name the returned-page population. Semantic alerts and static shell/login microcopy now use light foregrounds, although login placeholders remain below normal-text contrast. The runtime boundary is visible beside submission, but plan-only copy says sign-in values will not be sent even though the form still posts them through the web server to the Operations API.

**Watch for:** **Blocker:** [confirmed] plan-only submission still transmits an entered login pair to the server/API while the new footer says it will not “send sign-in values.” **Non-blocking:** [confirmed] login placeholders remain about 4.06:1; [confirmed] retry and timeline failure cues remain trapped in closed disclosures; [confirmed] required/optional field semantics remain visual-only; [confirmed] the new trust-boundary, digest-failure, metric, and contrast behavior lacks regression coverage.

## High-level view

Dark low-number semantic shades now provide fills while light high-number shades provide warning, success, and destructive text. Static shell/login microcopy computes between 6.45:1 and 7.71:1, but the shared `/70` placeholder treatment used by login computes to about 4.06:1.

The submit footer names “Self-hosted · Playwright” or “Managed cloud · Browser Use” and explains which runtime receives one-time sign-in values. Its plan-only branch accurately says no browser starts, but its unqualified no-send claim conflicts with the request path still posting `browser_login` to the Operations API.

The committed profile renders immediately before operator controls, and `AdmissionDecisionForm` appears only when its fetched digest exactly equals the onboarding digest. A failed request or mismatch leaves only an unavailable status; the backend digest check remains a second enforcement boundary.

“Recent active” excludes `execution_mode === "plan_only"`, counts nonterminal records in the returned items, and says “Live runs among latest N.” `listRuns()` requests 25 records and storage orders them newest-first, so the metric now identifies its paginated population.

Research/validation recovery and timeline failure still require opening disclosures. Optional labels remain hidden from assistive technology while required schema fields lack programmatic required state, and tests cover only happy-path DOM presence rather than the fixed security-sensitive branches.

<summary>Details</summary>

### Plan-only copy masks a browser-to-server credential hop (**blocker, confirmed**)

For plan-only submission, the footer says, “Plan-only mode will not start a browser or send sign-in values.” `NewRunForm.submit` nevertheless copies the email and password into `FormData`; `createRunAction` builds `browser_login` whenever an existing-account pair is present; and `createRun` serializes it into `POST /api/runs`. The backend neither starts a provider runtime nor persists/stages the pair in plan-only mode, but the values still cross both server boundaries before being discarded.

```text
entered login pair
      |
      v
Next server action --> Operations API --X--> browser runtime
                                      plan_only
```

Either omit `browser_login` for `plan_only`, or say it is not passed to a browser runtime while acknowledging that entered values reach the server. The pending label also changes from “Create plan” to “Starting agent…” after plan-only submission, weakening the same no-live-execution message.

### Dark semantic copy is repaired, but login placeholders remain sub-threshold (**non-blocking, confirmed**)

The repaired warning, success, destructive, and full-strength muted foregrounds all clear 4.5:1 on their dark surfaces. `Input` and `Textarea`, however, use `placeholder:text-muted-foreground/70` over `--field: #171717`; compositing `#a1a1a1` at 70% yields about `#787878`, or 4.06:1. Login’s “Operator username” and “Your password” placeholders therefore remain below the normal-text threshold. Use an opaque muted token or enough opacity to clear 4.5:1, then verify the rendered composition in a browser.

### Exact profile equality gates admission beside the rendered profile

The profile and run-detail requests can fail or advance independently. Rendering the profile before `OnboardingControlBar` and gating it with `profile?.profile_digest === onboarding.profile_digest` closes that race:

```text
onboarding.profile_digest --+
                            +-- exact equality --> AdmissionDecisionForm
fetched profile.digest -----+         |
                                      +-- absent/mismatch --> unavailable status only
```

The decision still submits the onboarding digest, so backend optimistic concurrency remains defense in depth.

### Recovery authority and audit failure remain hidden by default (**non-blocking, confirmed**)

Research and credential-validation retries remain inside the initially closed “Output and retry authority” disclosure, including when one is the only recovery action. Timeline retrieval failure appears only after opening “Run timeline,” while browser and email retries remain visible. Add an action/error cue to each summary or open it when it contains the only recovery or an unavailable audit stream.

### Required and optional semantics remain visual-only (**non-blocking, confirmed**)

`Field` renders “(optional)” with `aria-hidden="true"`, while required application, company, use-case, browser, policy, and run-mode controls have neither native `required` nor `aria-required`. Expose the optional marker and programmatically mark required controls without relying on native submission validation.

### Fix paths still lack regression coverage (**non-blocking, confirmed**)

Form tests do not assert the always-visible provider boundary, managed-runtime warning, plan-only copy, or plan-only payload. The admission test only exercises `admissionProfileAvailable=true`; there is no unavailable/mismatched-digest or page-order case. No dashboard test combines plan-only and live records on a partial page, and DOM tests cannot establish rendered contrast.

`git diff --check -- web` passed, but this checkout did not provide clean release validation: duplicate ignored `.next/types/* 2.ts` declarations block type checking, affected Vitest suites terminated before results, and lint/build exited without actionable diagnostics while an existing Next dev server was active. Re-run affected tests, lint, typecheck, build, and browser contrast checks in a clean checkout or CI.
